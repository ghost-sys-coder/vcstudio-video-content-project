# VCStudio

## Project overview

This repository is the foundation for an internal production tool that converts narration scripts into structured scenes, generated media, synchronized timelines, and rendered videos.

## Current capabilities

- Public marketing landing page (floating nav, dot-grid hero with a pipeline mockup panel, six-step workflow explainer, a dark feature band with an orbit illustration, an approval-checkpoint mockup section, closing call-to-action), public `/privacy`, `/terms`, and `/data-deletion` legal routes, visible footer legal links, and shared Clerk sign-in/sign-up presentation.
- Lazy Clerk user synchronization into PostgreSQL.
- Signed, idempotent Clerk user lifecycle webhook processing.
- First-workspace onboarding with transactional owner membership creation.
- Authenticated application shell, workspace selector, user account menu, a data-driven workspace dashboard, and access-denied state.
- Central `owner`, `editor`, and `viewer` authorization policies.
- Private Cloudflare R2 workspace-logo uploads with a 5 MB limit and object cleanup on replacement or deletion.
- Responsive shadcn application sidebar with persistent desktop collapse state, a mobile drawer, and a light/dark theme toggle that persists per signed-in user in PostgreSQL (with a cookie fast-path so every route, including public pages, renders the correct theme with no flash).
- Custom 404 handling via a shared `NotFoundState` component: `app/not-found.tsx` covers unmatched URLs outside the app shell, and `app/(authenticated)/app/not-found.tsx` covers a `notFound()` call from inside the app (e.g. a deleted or foreign project/character) while keeping the sidebar and workspace context on screen, linking back to the dashboard instead of the marketing homepage.
- Owner-only workspace profile management for workspace names and private logos, plus workspace membership management: inviting teammates by email (via Clerk's own sign-up invitation delivery, not a custom email pipeline), assigning `owner`/`editor`/`viewer` roles, changing an existing member's role, removing a member, and revoking a pending invitation — with a standing invariant that a workspace can never end up without at least one owner.
- Workspace-scoped project creation, pagination, settings, status transitions, and archiving.
- Owner-only permanent project deletion from a **Danger zone** on the project settings page. A confirmation dialog spells out exactly what is destroyed (scenes, script versions, generated images and audio, subtitles, renders, shorts, thumbnails, and publish history), then the app cancels any still-running background jobs for the project, erases every stored file under the project's R2 prefix, and removes the database rows. Characters and their artwork are shared across projects and are deliberately untouched. The audit trail survives the project it describes.
- Optimistically locked script drafts with immutable version numbering, restore-as-new-version behavior, and audited owner/editor soft deletion of eligible versions.
- Idea Lab (`/app/ideas`), a top-level workspace page outside the projects tree for brainstorming video ideas before a project exists. Owners/editors describe a niche — typed freely or picked from a curated sample of proven niches that auto-populates the field — (optionally with a target platform, tone, and count) and generate a batch of distinct idea cards in one shot; each card is a pre-project brief carrying exactly the fields a project brief needs (topic, audience, tone, target duration, primary platform, hook angle) plus a short rationale and hook type. Saved ideas are grouped by niche in a library, and the **Create project** dialog's **Start from a saved idea** selector (cross-workspace-guarded) seeds a brand-new project's brief from a chosen idea, so a saved idea seeds script generation without retyping — there is deliberately no way to apply a saved idea to an already-created project, since a blank project has no use for it once it exists. Idea generation reuses the OpenAI text model, runs as a plain server action (no Trigger.dev task), is rate-limited, and — because it is a sub-cent one-shot call — is deliberately kept **off** the usage-reservation ledger like publishing, recording its actual cost in `content_idea_generation_runs` for visibility. The prompt encodes proven, high-retention formats and is deliberately honest: it never claims an idea is guaranteed to go viral or is currently trending. A historical niche also switches idea generation into a factual-accuracy mode: every idea's premise must be a real, verifiable event or figure.
- Per-project content brief (topic, audience, tone, target duration, primary platform, hook angle, niche) and cost-confirmed AI script generation: a brief-driven, money-safe `script_generation` operation (OpenAI Responses API structured output on the `ai-text` queue, on the usage ledger) drafts a narration-ready script that is inserted non-destructively into the existing script editor for review, editing, and versioning. Encodes proven hook-first/retention heuristics — presented as suggestions, not guaranteed performance. A historical niche/topic/hook angle switches generation into a strict factual-accuracy mode: verifiable events only, no invented quotes/statistics, disputed details flagged rather than stated as fact.
- Per-platform publishing-metadata generation on the **Publish** tab: the existing money-safe `title_generation` operation now turns the brief and approved script into ranked titles, a publication-ready description or caption, and a restrained set of relevant tags for YouTube, TikTok, Facebook, or Instagram. Each explicit generation remains cost-confirmed and durable. Selecting a connected channel automatically loads the latest set into editable platform-specific drafts, prefers a favorited title, refreshes after generation or favorite changes, and preserves user edits while switching channels; completing a newly requested generation deliberately replaces that platform's older draft with the newly paid result. YouTube receives native title/description/tags, Facebook appends the editable topic tags as hashtags to its description, Instagram composes its editable caption and hashtags, and TikTok exposes editable suggestions for copying because inbox upload cannot transmit metadata.
- Per-platform thumbnail generation on the same **Publish** tab: a money-safe `thumbnail_generation` image operation (OpenAI image model on the `image-generation` queue, on the usage ledger) renders cover images at each platform's native size — 16:9 for YouTube/Facebook, 9:16 for TikTok/Instagram — in either a **text-free** mode (deliberate negative space for overlaying a headline later) or a **baked-headline** mode (one short headline rendered into the image). Results accumulate into a per-platform gallery with favorites and authenticated signed-URL download; owners/editors see the cost before confirming and can cancel a not-yet-started generation. Images are stored in private R2 under `workspaces/{ws}/projects/{proj}/thumbnails/{platform}/{id}.{ext}` and served only through a workspace-scoped redirect route. The prompt encodes proven composition heuristics (single expressive face, strong readable emotion, high contrast, rule-of-thirds, minimal clutter, directional gaze) — presented as A/B-test candidates, not guaranteed performers — and the UI warns that baked text can be rendered imperfectly. In baked-headline mode the UI also offers suggested headlines in a `Select`, condensed from that platform's already-generated titles (favorites first) and the brief's hook angle and topic; picking one fills a headline field that stays freely editable, so a suggestion is a starting point rather than a fixed choice. Suggestions are derived from existing content, so they add no provider call and no cost.
- Publishing a finished render to a connected YouTube channel, Facebook Page, Instagram professional account, or TikTok creator from the project **Publish** tab. Long-running publication state survives navigation: returning to the page restores the connection and render from the newest active publication, polls persisted progress until the job reaches a terminal state, and labels the action from that exact target rather than whichever connection happens to appear first. Publish history shows stage badges plus a visible, accessible percentage bar throughout uploading and platform processing. TikTok uses the least-privilege `user.info.basic` and `video.upload` scopes and sends a compatible MP4 to the creator's TikTok inbox only after explicit consent; it does not use Direct Post, and the creator finishes the post in TikTok. The durable worker stores resumable provider state before transfer, reconciles retries against provider progress, and streams private R2 videos in bounded ranges. Disconnection destroys stored tokens while preserving non-secret publication history and attempts TikTok revocation. Uploads cost no credits, so publishing deliberately does not touch the usage-reservation ledger. When YouTube is the target, the render picker and publish panel also show whether the selected render will land as a YouTube Short (vertical or square, 3 minutes or under) — advisory only, since unlike Instagram/TikTok, YouTube accepts both long-form and Shorts through the same upload and a non-eligible render remains fully publishable as a regular video.
- Route-backed project tabs and a bounded, internally scrollable long-script editor.
- Approved script versions, cost-confirmed Trigger.dev scene analysis, crashed-run reconciliation and retry, schema-constrained OpenAI output, editable immutable scene versions, and scene approval.
- Searchable two-pane scene navigation with URL-addressable selection, status filtering, approval progress, and unsaved-change protection.
- Workspace-scoped character profiles, private validated R2 reference galleries, archival, and immutable scene-version character assignments.
- Project cast for character consistency: a per-project roster of characters that scene analysis auto-matches to scenes by name (article/case/plural tolerant), a "Project cast" panel on the scenes page (owner/editor) to add/remove characters and bulk-apply the cast to matched or all scenes without disturbing existing assignments, automatic re-application of the cast to freshly analyzed scene versions, and pre-selection of each assigned character's canonical reference image so scene-image generation stays consistent by default.
- Generated character reference portraits: owner/editor generation of canonical identity images (master, front, three-quarter, side, full-body) directly from a character's structured description using the OpenAI Images API, saved as `generated` reference assets that flow into the reference gallery and scene generation. Portrait spend is workspace-scoped (a character has no project), so it is guarded by an advisory-locked workspace daily/monthly budget preflight and tracked on its own `character_reference_generations` record with per-view cost estimates shown before confirmation — it is intentionally not part of the project-scoped usage dashboard.
- Validated character JSON import from pasted content, local files, or a built-in sample.
- Versioned scene-image prompts and workspace style presets, cost-confirmed single-scene GPT Image generation, exact character-reference snapshots, private R2 assets, review history, and atomic per-scene-version approval.
- Draft (`low`), final (`medium`), and explicit high-quality image modes using only the supported landscape, portrait, and square OpenAI sizes. A scene is no longer limited to one image: owners/editors select **multiple sizes at once** (in both the single-scene workspace and storyboard bulk generation) and each selected size becomes an independent, separately-billed OpenAI generation — never a crop of another size. Each size can be approved independently (one approved image per `(scene version, size)` pair), and the review UI groups a scene's generation history by size. When rendering an output variant (e.g. a 9:16 Short) whose target size already has a natively-generated approved image, the render uses it directly and skips the free crop and paid AI-outpaint steps entirely for that scene — the Scene Framing editor shows an explicit notice when this applies. Falls back to the existing crop/outpaint system exactly as before when no native match exists at the exact target size.
- Storyboard grid with controlled bulk image generation: per-scene selection and status filtering, a size multi-select, a confirmation dialog showing scene × size image count, a per-size cost breakdown, and remaining budget, a live batch-progress panel (queued/running/succeeded/failed/cancelled with actual cost), per-scene regenerate/retry, bulk and per-scene approval, and cancellation of not-yet-billed queued generations. The batch image-count limit counts total images requested (scenes × sizes), not scenes alone.
- Per-scene narration audio (OpenAI text-to-speech) with workspace voice presets, single and bulk generation, cost confirmation and budget enforcement, audio playback and review/approval, FFprobe-measured durations, and a deterministic project timeline (ordered scenes, configured padding, millisecond and frame boundaries without cumulative drift).
- Manual media as a free alternative to AI generation, on the Storyboard page, the Scenes page's per-scene **Images** tab, and the Audio page, flowing through the exact same review/approve pipeline as AI output (`source: "ai_generated" | "user_uploaded" | "user_recorded"` on each generation row) with no usage-reservation or budget involvement, since neither is billable: owners/editors can **upload an already-made image** for any scene/size — from either the Storyboard grid or a scene's own Images tab, sharing one `SceneImageUploadDialog` component — validated by content type, size limit, and a tolerant aspect-ratio check against the target size (not pixel-exact like AI output), as an alternative to generating one; and can **record narration in the browser** on the Audio page — a dialog shows the scene's full narration text to read along, records via `MediaRecorder`, and — when AI or a prior recording already exists — plays both back side by side before the user chooses to save (submits for review, same as AI output) or discard. AI generation/regeneration is unaffected on either page. Outpainting remains AI-source-only: it requires the approved image to have come from AI generation, since there is no known style to extend from an arbitrary upload.
- Deterministic subtitles and a typed video timeline contract: captions are derived from each scene's approved narration audio (scene- or sentence-level segments, timing distributed across the measured audio duration by character proportion — never fabricated word timestamps), with editable per-cue text overrides, a configurable caption style (font, size, colors, position, safe margin, casing) and live preview, SRT and WebVTT export, Remotion caption input, and a `VideoTimeline` builder that assembles approved image + audio + captions + camera motion + transition per scene, rejects construction when any approved asset is missing, and returns an actionable per-scene validation report.
- Workspace usage administration (owners and editors): a `/app/usage` dashboard showing month/day spend, reserved and settled totals, spend by operation and by project, and day/month budget progress; editable per-workspace budgets, a manual-confirmation threshold, and operational-limit overrides; and paginated, filterable usage-ledger and audit-log views. Budgets and limits are enforced through the same money-safe reservation path they configure, and the manual-confirmation threshold gates the bulk generate dialogs.
- Remotion video preview and durable rendering: an in-browser Remotion Player preview of the assembled video (scene stills under deterministic subtle camera motion, cut/fade transitions, burned-in captions, narration audio, optional watermark, toggleable safe-area guides), landscape/vertical/square output presets at configurable frame rate, cost-estimated and budget-reserved render start that freezes an immutable timeline snapshot, a concurrency-one Trigger.dev rendering queue that bundles the composition and drives a headless Chromium, private R2 MP4 exports with authorized signed downloads, live render progress, failure surfacing, and an expired-reservation reconciler.
- Reusable multi-format outputs and Shorts: every source project owns landscape, vertical, and square output variants that reuse the same approved scene images, narration, and subtitle timing. Owners/editors can set provider-free per-scene fill/show-all framing, deterministic focal points, scale, and background color for each output — the focal point can be set by clicking or dragging directly on the image preview (with a visible marker) as well as with the original percentage sliders, both writing into the same value; a "Reset to default" button snaps a scene back to centered/100%/cover without saving; the scene chip strip shows a status dot per scene (customized framing, or outpaint queued/failed) so every scene's state is visible without clicking into each one; and one scene's framing can be bulk-applied to several other scenes at once via a checkbox multiselect, useful when many scenes share the same subject position. When framing is insufficient, they can explicitly confirm a conservatively estimated paid AI outpaint; it uses the exact approved source through OpenAI image editing, creates a separately versioned generation and R2 derivative, reconciles actual cost, and never replaces the approved original. A precise Shorts editor lets owners/editors multiselect several scenes at once (checkbox list with a live combined-duration total, replacing an earlier single-scene dropdown), add them in scene order, then reopen any added clip through a chip-strip selector to trim its exact range, choose cut/fade, and see the change reflected immediately in the clip list — defaulting to scene/subtitle-boundary snapping, trimming the existing approved audio, rebasing intersecting captions, previewing the vertical result, and sending it through the same cost-confirmed durable render path. Exact cuts crossing a caption cue are retained with an actionable warning rather than fabricating word timestamps. A saved short can also be reopened later and re-edited — its clip list is wholesale replaced on save, which is always safe since renders resolve a short's clips fresh at render time.

- Animated character videos. A project chooses a **video type** at creation (and can change it in settings): _Still images_ generates one AI image per scene as before, while _Animated characters_ generates each scene's image as an empty **background plate** and composites character sprites over it at render time. Characters are staged per scene (left/center/right) with one marked as **speaking**; the speaker's mouth is driven by the narration audio's measured loudness, non-speakers idle and blink on a staggered timer, and a two-hander automatically mirrors the right-hand character so the pair face each other. The choice is a property of the whole project, so a single video can never mix the two looks. Animated scenes render in the browser preview as well as the final export, so iteration costs nothing.
- Animated character pose generation: a character's reference-generation pipeline can also generate four matched animation-pose stills (idle, talk-open, talk-closed, blink) at a fixed canvas size on a **transparent background**, each anchored to the character's existing approved front/master portrait as an image-edit reference for pose-to-pose consistency, from the Characters page. These are the sprites the animated renderer composites.
- **Animation check** on each character's page: an on-demand pre-flight test that reads the four stored pose stills back out of R2, decodes them, and reports four pass/warn/fail checks — all four poses exist, each carries an alpha channel, each is _genuinely cut out_ (measured transparent-pixel share, not the requested background setting), and all four share the same dimensions. It then plays the character through the production sprite over a transparency checkerboard, driven by a synthetic speech envelope, with a mirror toggle for the facing transform. Run it before setting a project to _Animated characters_: the check spends nothing, whereas discovering a painted-in pose set after the fact wastes a set of background plates and a render.

- **Workspace media library** (`/app/social/library`), the first screen of a new **Social** sidebar segment that sits beside the video pipeline rather than inside it. Owners/editors upload reusable images (JPEG, PNG, WebP, GIF) and videos (MP4, MOV, WebM) once and keep them at workspace level, ready to attach to a social post; SVG is deliberately excluded because it can carry script. Uploads go straight to private R2 through a signed `PUT` whose content type and byte length are both signed, using the same three-step authorize → upload → confirm pattern as scene images. Confirmation re-derives the truth from storage rather than trusting the browser: the real byte length from a `HEAD`, and for images the real decoded dimensions from `sharp`. Each asset carries an editable title, **alt text** (carried through to platforms that accept it), and comma-separated tags. Removal is a soft delete — the row and the stored object both survive, because a post that already published must keep showing the media it sent. Library keys live at `workspaces/{ws}/library/{assetId}.{ext}`, deliberately outside the project asset prefix, so deleting a project can never purge library media.

- **Social post composer** (`/app/social/posts`). A post is written once, in a rich text editor, and previewed per destination before it goes anywhere. The catch it is built around: **the platforms accept plain text**, so the composer stores a structured document and renders it down to the exact string each platform will receive — bold and italic are dropped, list items become bulleted or numbered lines, links flatten to `label (url)` or a bare URL. Those previews sit beside the editor while writing, so the formatting that will be lost is visible rather than discovered afterwards. Formatting is deliberately **not** faked with Unicode math-alphanumeric characters: they defeat screen readers and are not indexed by platform search. Destinations are gated by a **capability matrix** rather than a flat checkbox list, because the five platforms are not interchangeable — LinkedIn and Facebook take text on its own, Instagram requires media, and TikTok and YouTube require a video (YouTube has no public Community Posts API at all, so a YouTube target is a video upload). Each ineligible platform shows its reason and its character ceiling. Drafts are optimistically locked, so a second open tab is told it is stale instead of silently overwriting.

- **Publishing and scheduling social posts** to LinkedIn (new), Facebook Pages, Instagram, TikTok, and YouTube. A post fans out to one durable background job **per destination**, so a LinkedIn success and an Instagram rejection are independent outcomes with independent retries — and the post reports `partially_failed` rather than hiding three successful sends behind one error. Scheduling is a **database sweeper**, not a delayed job: `scheduled_at` lives in PostgreSQL and a `social-post-scheduler` cron claims due posts atomically (`FOR UPDATE SKIP LOCKED`), so rescheduling and cancelling are plain updates, a lost background run cannot orphan a post, and a post scheduled while the worker was down still goes out on recovery. Destinations are validated against the capability matrix at schedule time, while the author is present to fix a problem, rather than at 6am on Thursday. Posting costs nothing, so — like video publishing — it is deliberately **off** the usage-reservation ledger and rate-limited instead. `ENABLE_SOCIAL_POST_SIMULATION` runs the whole compose → schedule → publish loop against a simulator with no real API call, which is what makes the flow verifiable before LinkedIn approves an app.

- **Sharing a render as a social post** from a project’s publish page. LinkedIn accepts posts, not rendered-video uploads, so it never appears in the video channel picker — the publish page instead has a _Share as a social post_ panel that lists the post-capable connected accounts (LinkedIn included), takes a finished render and some commentary, and creates a draft post carrying that render. It then opens the composer rather than publishing on the spot: destination selection, the per-platform previews, the character counters, and scheduling already live there, and a second publish path would give the capability matrix a second place to disagree with itself. A render is attached **by reference**, not copied into the library — `social_post_media` holds either a `media_asset_id` or a `render_id`, with a database CHECK enforcing exactly one — so sharing a 500 MB export does not duplicate 500 MB of storage.

## Architecture

The application is a TypeScript modular monolith. Next.js owns web routes and server functions, Clerk provides authentication, and Neon PostgreSQL is authoritative for application users, workspaces, memberships, roles, and active-workspace authorization. Database access is isolated in repositories, queries, and commands; authorization policies live outside React components.

The repository will move into the full `apps/` and `packages/` monorepo structure during the broader bootstrap phase. Phase 1 uses the current root Next.js application without introducing a second application structure prematurely.

## Technology stack

Next.js 16, React 19, strict TypeScript, Tailwind CSS, shadcn/ui, sonner (toast notifications), Clerk, Neon PostgreSQL, Drizzle ORM, Trigger.dev 4.5.4, OpenAI Responses API, Cloudflare R2, Sharp, Remotion 4 (`remotion`, `@remotion/player`, `@remotion/bundler`, `@remotion/renderer`), Zod, Vitest, ESLint, and Prettier.

## Local setup

1. Install Node.js 20.9 or newer.
2. Run `npm install`.
3. Copy `.env.example` to `.env` and supply the required values.
4. Run `npm run db:migrate` after reviewing the generated migration.
5. Run `npm run dev` and open `http://localhost:3000`.

## Storage setup

Workspace-logo storage uses a private Cloudflare R2 bucket. Objects use workspace-scoped keys such as `workspaces/{workspaceId}/branding/logos/{assetId}.png`; PostgreSQL stores metadata and ownership rather than image bytes or permanent public URLs.

Character references use keys such as `workspaces/{workspaceId}/characters/{characterId}/references/{referenceType}/{assetId}.webp`. Completion downloads the private object and uses Sharp to verify its real format and dimensions before persisting metadata. Core identity views replace their prior object; expression, outfit, and pose references allow multiple images. Deleting or replacing a reference removes its R2 object.

Generated scene images use deterministic keys such as `workspaces/{workspaceId}/projects/{projectId}/scenes/{sceneId}/versions/{sceneVersionId}/images/{generationId}.webp`. The Trigger.dev task verifies the generated bytes and dimensions before upload, stores recovery metadata on the private R2 object, and exposes images only through an authorized short-lived download route. Exact selected character-reference asset identifiers and immutable object metadata are retained with each generation record.

Configure the bucket CORS policy to allow `PUT` from every browser origin that uploads directly to R2, including `http://localhost:3000` and the stable production origin `https://vcstudio.veilcode.studio`, with the `Content-Type` header. Deployment-specific preview URLs must be added explicitly before uploads will work from previews. Upload URLs expire according to `R2_SIGNED_UPLOAD_EXPIRY_SECONDS`; private logo display uses short-lived signed download URLs. Logo uploads accept PNG, JPEG, and WebP files up to 5 MB. Replacing or deleting a logo removes the superseded R2 object.

## Rendering setup

Rendering uses Remotion 4. The in-browser preview renders the composition with `@remotion/player`; the durable render runs in the Trigger.dev `video-render` task, which bundles the composition with `@remotion/bundler` and encodes with `@remotion/renderer` (H.264 via the ffmpeg build extension) driving a headless Chromium. The renderer and bundler are declared in `serverExternalPackages` so they never enter the Next.js bundle — only the `video-render` task imports them. Supported outputs are 1920×1080 landscape, 1080×1920 vertical, and 1080×1080 square at the project's frame rate; the render always uses the project's aspect ratio because scene images are generated at that ratio. Set the Phase 9 render variables in both Vercel and Trigger.dev (encoder/browser settings are Trigger.dev-only). The end-to-end Chromium render can only be validated by deploying the task; local verification covers typecheck, lint, unit tests, the production build, and the opt-in PostgreSQL render-invariant suite.

The preview player is buffering-aware to avoid a stuttering first playback. Preview asset URLs are signed for the whole session (`VIDEO_PREVIEW_URL_EXPIRY_SECONDS`, Vercel-only) so they never expire mid-play. A rolling preloader (`use-render-preload-window`) prefetches the first ~25 seconds of scene stills, narration, and the caption font before playback is allowed, then keeps a ~30-second window ahead of the playhead while freeing assets far behind it — the full project is never downloaded up front. Playback is gated behind a visible "Loading preview" overlay with disabled controls until the initial window is ready, never autoplays, and pauses (showing a poster) whenever the current still or narration has not buffered. Incoming scenes are premounted ~1.5 seconds before their transition so both scenes exist during the overlap. Load, decode, and buffering transitions are recorded to in-memory preview telemetry (echoed to the console when `localStorage['preview:verbose']` is `'true'`). To verify a smooth first playback, open the render page in a fresh incognito window with the cache disabled and confirm transitions play correctly on the first pass, not only on replay.

## Security model

Facebook OAuth state is checked against both the authenticated user and active workspace. Page selection uses a short-lived encrypted HttpOnly cookie; the server re-fetches the authorized Page list before persisting a selected Page token, so Page identity and credentials are never trusted from browser form data. The Meta app secret remains Vercel-only and is not sent to Trigger.dev.

Platform publishing credentials are treated as first-class secrets. OAuth access and refresh tokens are sealed with AES-256-GCM (`lib/crypto/secret-box.ts`, random per-message IV, authenticated so tampering is rejected) before they reach PostgreSQL, and the sealed columns are excluded from the read-model projection so a connection can never reach a React component carrying a credential. TikTok's ephemeral upload URL is also sealed while a transfer is resumable and cleared on terminal completion or failure. The OAuth `state` parameter is HMAC-signed, expiring, and platform-bound. Connecting and disconnecting channels requires the owner-only `manageSettings` capability; editors may publish through an existing active connection but cannot change workspace credentials. TikTok disconnect attempts provider revocation and still destroys local credentials if the provider is unavailable. Provider error bodies are never echoed into redirects. The publish worker signs the R2 source URL for longer than its own wall clock so an upload cannot die on an expired URL mid-stream.

Clerk authenticates sessions; PostgreSQL authorizes application access. Every protected server resource calls Clerk protection and then resolves the local user. A workspace ID from a cookie or form is only a preference and is never trusted: every workspace operation queries membership by both `userId` and `workspaceId`. Workspace creation and initial ownership are transactional. Webhooks are verified before parsing, deduplicated by Svix delivery ID, and store only safe failure summaries.

Deleted Clerk users are soft-deleted and anonymized locally so workspace ownership and audit relationships remain intact. Script-version deletion is restricted to owners and editors, scoped by the authenticated workspace, and records the deleting user and timestamp.

Scene-image configuration, generation history, reference selection, asset delivery, approval, and rejection are authorized by workspace-scoped project and scene identifiers resolved on the server. Composite foreign keys also prevent Phase 5 generation, reference, provider-attempt, reservation, and usage-event rows from crossing workspace or project boundaries. Only owners and editors can generate or review images. Private reference and generated-image objects are never exposed as permanent public URLs.

Billable and mutating operations are protected by a per-workspace fixed-window rate limiter (`rate_limit_counters`, enforced in the web runtime before any reservation is created), and the authenticated app renders a safe error boundary that never exposes provider or internal errors to users. Object storage handling, signed-URL lifetimes, deterministic cleanup, and orphan/stale reconciliation are documented in [`docs/storage-lifecycle.md`](docs/storage-lifecycle.md).

Video renders and exports are workspace-scoped by composite foreign keys and are gated by the `renderVideo` capability (owners and editors only). The export bucket is private: downloads flow through an authorized route that resolves the render by both workspace and project, confirms it succeeded and owns a workspace-scoped object key, and only then redirects to a freshly minted short-lived signed URL. Signed asset and export URLs are never logged, and the render timeline snapshot stores object keys rather than signed URLs so a persisted render never leaks credentials.

## Cost controls

Scene analysis and scene-image generation show a conservative estimate before confirmation. Their reservation commands serialize spending checks per workspace, enforce project plus daily and monthly workspace limits atomically, and append application-level ledger events. Image generation records each provider attempt and actual token usage, reconciles the reservation to actual cost, releases unused value, and uses a conservative reserved-cost fallback when usage is unavailable. Every explicit Generate action creates a new paid generation version; billable retries are bounded by `MAX_IMAGE_GENERATION_RETRIES` and never silently reuse an older image.

Video rendering has no per-render provider invoice, so its cost is derived from output duration at `VIDEO_RENDER_COST_PER_MINUTE_CENTS` (rounded up to the minute, with a minimum floor) and shown before the render starts. Starting a render reserves that estimate through the same money-safe ledger under a per-workspace advisory lock and project/daily/monthly budget guard, then reconciles to the same figure on success or releases it on cancellation, expiry, or pre-compute failure. Renders longer than `MAX_RENDER_DURATION_SECONDS` are rejected before any compute, billable retries are bounded by `MAX_RENDER_ATTEMPTS`, and an identical timeline reuses its existing render rather than billing again.

Workspace budgets are editable from the owner/editor `/app/usage` dashboard. Each workspace can persist a `workspace_budget_settings` row (daily budget, monthly budget, a manual-confirmation threshold, and optional per-workspace operational-limit overrides for images-per-batch, scenes-per-audio-batch, and max render seconds); when absent, the `DEFAULT_DAILY_BUDGET_CENTS`/`DEFAULT_MONTHLY_BUDGET_CENTS` environment defaults apply and the limit overrides fall back to their env defaults. Estimates at or above the manual-confirmation threshold require an explicit extra confirmation in the bulk generate dialogs before spending. Every reservation preflight and the money-safe reservation command read the same resolved budget (`loadEffectiveWorkspaceBudget`), so the UI's disable state and the server-side budget guard never diverge. The unified usage ledger is a read-only view derived by joining each `usage_reservations` row to its operation table (user, provider, model, units, provider request id, and workflow run id), and every budget change plus key mutations are recorded in an append-only audit log whose metadata is sanitized to exclude secrets and signed URLs.

## Current limitations

- Billing is intentionally excluded from Phase 1.
- `CLERK_WEBHOOK_SIGNING_SECRET` must be configured before real webhook delivery can succeed.
- The Phase 1 migration must still be applied separately to future preview and production databases.
- Full browser end-to-end coverage will be expanded with the bootstrap Playwright foundation.
- The end-to-end Remotion render runs only in the deployed Trigger.dev worker (headless Chromium via a build extension); it cannot be exercised locally. The Chromium `aptGet` package list and the `additionalFiles` bundled-source paths in `trigger.config.ts` must be validated on first deploy, and the whole task is gated by `ENABLE_VIDEO_RENDERING`.
- Render output always uses the project's aspect ratio; the other format presets are shown but disabled because scene images are generated at the project ratio. Camera motion and transitions are assigned deterministically per scene rather than authored per scene.
- Subtitle word-level timing is intentionally never synthesized; captions use scene- or sentence-level timing distributed across the measured audio duration. Per-cue timing is not hand-editable (only cue text), because timing is always recomputed deterministically from approved audio.
- Phase 5 generates one scene image per confirmed request. Batch generation and a workspace style-preset editor are deferred; the immutable seeded preset and generation history are available now.
- AI outpainting currently extends one scene at a time and uses the configured draft image quality. Batch outpainting and a manual quality override are intentionally not exposed, limiting accidental spend.
- Script version history is currently bounded to the latest 50 versions in the editor.
- Approved script versions and versions referenced by scene analysis are retained and cannot be deleted.
- Trigger.dev must be running locally or deployed before queued scene analyses or image generations execute.
- TikTok delivery is inbox-only: VCStudio cannot select TikTok privacy or publish automatically, and the creator must finish the post in TikTok. The initial implementation uses server-side `FILE_UPLOAD`; eligible renders must be MP4, 360-4096 pixels per dimension, 23-60 FPS, no longer than 10 minutes, and within the application's configured upload-size ceiling.
- Uploaded scene images and recorded narration cannot be the source of an AI outpaint (no known style to extend from an arbitrary file); AI-generated images are unaffected.
- Animated characters are **positioned, not animated through space**: they stand in one of three stage slots and pose-swap in place. There is no locomotion (walking across a room), no environmental interaction (picking things up, opening doors), and no gesturing beyond the four pose stills. The look is cutout animation over painted backgrounds — a deliberate, cost-driven choice over generative video, which was rejected because character identity drifts between independently generated clips, it bills per second of output, and it cannot be told to lip-sync to pre-recorded narration. Expanding the pose library (gesturing, pointing, turned views) is the natural next lever and needs no architectural change.
- Lip-sync only works for **AI-generated narration**. Audio recorded through the in-browser recorder gets no amplitude envelope, because that upload completes in a Vercel route handler where ffmpeg is unavailable; those scenes render the character idling. Moving that measurement into a background task would close the gap.
- Converting an existing project to animated does **not** regenerate its scene images — that would silently spend money. Images generated while the project was a still-images project still contain the characters, so they must be regenerated as plates explicitly, or the cast will appear twice.
- There is no review/approval gate on generated pose stills (they go live immediately, like existing character reference portraits). Pose-to-pose visual consistency, and how cleanly the transparent background cuts out, both depend on the image model obeying the prompt; nothing validates either after generation.
- The browser narration recorder (`useSceneAudioRecorder`) has no automated test — this repo's Vitest config runs in a plain Node environment with no jsdom/browser-API test infrastructure, and adding one for a single hook was judged out of scope for this change.
- **LinkedIn posting needs an approved LinkedIn app** — the "Share on LinkedIn" product for member posts. Credentials being present is not the same as the product being approved: `w_member_social` is only granted once LinkedIn approves it, and until then the consent screen rejects the scope. Approval is not instant, and until it lands the LinkedIn provider cannot be exercised live. `ENABLE_SOCIAL_POST_SIMULATION=true` runs the entire flow against a simulator so nothing else is blocked behind it. Posting as an **organization page** is not implemented: it needs `w_organization_social` and the Community Management API, a separate LinkedIn approval.
- **Two new Trigger.dev tasks need a dev and a prod deploy** (`social-post-publish`, `social-post-scheduler`) before publishing or scheduling does anything. Without a running worker the app still dispatches — the target row reaches `queued` and gets a `trigger_run_id` — but nothing executes and the panel polls forever. This is the same failure mode already documented for `video-publish`.
- Scheduling has up to about **a minute of jitter**: the sweeper runs on a one-minute cron, so a post scheduled for 09:00 goes out between 09:00 and roughly 09:01. This is the deliberate cost of keeping the schedule in PostgreSQL rather than in a delayed background run.
- A **per-platform copy override** exists in the schema (`social_post_targets.override_body_plain_text`) and is honoured by the publish worker, but nothing in the composer sets it yet — every destination currently receives the same body.
- **Instagram and TikTok post rules are enforced at two levels only**: the capability matrix (media presence, counts, character limits) and whatever the platform itself rejects. Aspect-ratio and codec rules are not pre-checked for post media the way they are for renders, so a non-conforming image or video fails at publish time with the platform's own reason.
- A media library **video's duration and dimensions cannot be verified server-side**. There is no ffprobe in the web runtime, so duration is read from a `<video>` element in the browser and treated as an untrusted hint: it is range-clamped on the server and each platform re-validates it at publish time. Images are fully verified (`sharp` decodes the stored object for real dimensions).
- `npm run db:migrate` currently **fails**: the `drizzle.__drizzle_migrations` journal records 30 migrations while 43 exist on disk, because later schema changes were applied with `drizzle-kit push`. Replaying from the journal therefore re-runs already-applied DDL (`CREATE TYPE "content_idea_source"` fails first). Schema changes are applied with `npx drizzle-kit push` and hand-verified against `pg_indexes`/`pg_constraint`. Reconciling the journal is worth doing before the first production deploy, since production has no `push` history to fall back on.
- Safe npm overrides pin vulnerable `ws` and `cookie` transitive dependencies to patched releases. The dependency tree currently retains 32 moderate transitive advisories in Trigger.dev OpenTelemetry/esbuild, Next.js PostCSS, and Clerk UI dependency chains. The development-only Trigger.dev CLI adds four high `tar` advisories; npm currently offers only breaking forced downgrades rather than compatible remediations.
