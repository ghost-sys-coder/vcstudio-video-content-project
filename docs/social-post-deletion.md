# Social post deletion

Owners and editors can delete a saved Social post from its card, calendar card or editor using the shared shadcn confirmation dialog. Viewers cannot request deletion details or delete posts. The dialog initially focuses Cancel, loads saved details only when opened, and shows loading, pending and recoverable error feedback. It prevents duplicate submission and dismissal during deletion.

Deletion removes the VCStudio post and its local attachment, destination and delivery records. A scheduled post disappears from the calendar and cannot be claimed for later dispatch. Already published copies on social platforms remain there; this action does not call a platform deletion API. A post that is publishing, has queued/publishing targets or a pending YouTube thumbnail, or carries an MCP execution lock cannot be deleted. The server checks the saved revision again in the atomic mutation, so a concurrent edit, schedule claim or approval prevents stale deletion.

If the saved post has media, including a separately selected YouTube thumbnail, the dialog offers **Also delete attached media from the library**. This is unchecked by default. With no media, the option is absent. If every attachment is shared or project-owned, the option is disabled with an explanation. Unsaved attachment choices do not affect the saved-post deletion preview.

Selecting the option soft-deletes eligible library assets, following the existing library's retention policy. Their records and private R2 originals/thumbnail objects remain retained; this is removal from the library and future selection, not a storage purge. Project-owned renders and assets referenced by another post or thumbnail, project media, video generation, MCP scene reuse or historical Marketing content are preserved. Reference checks run again at deletion, so files shared since preview are kept. Historical Marketing reference checks do not load Marketing workflows or activate the paused studio.

The mutation scopes every lookup to the authenticated workspace, requires `composePosts` and additionally `manageMediaLibrary` for media removal, and records the post's former status and removed media IDs in the audit trail. It uses one PostgreSQL statement for deletion and optional library removal. No migration, new environment variable, provider call, worker deployment, background job or MCP deletion tool is required.

Verification uses isolated PostgreSQL and mocked browser/server requests. Never delete a real production post or file just to verify the interface. Relevant checks include tenant and role isolation, stale versions, scheduling locks, attachment/thumbnail counting, shared references, keyboard cancellation, retry behavior, explicit media opt-in and responsive Light/Dark layouts.
