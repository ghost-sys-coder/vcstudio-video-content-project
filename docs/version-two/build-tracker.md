| Status        | Meaning                                                                              |
| ------------- | ------------------------------------------------------------------------------------ |
| Not started   | No implementation work or acceptance evidence yet                                    |
| In progress   | Active implementation; record owner and next action                                  |

Existing approved-version history controls remain available when the editor is settled.

### V2-03 — Verified script-to-scene fidelity

- Owner: Claude. Started / last updated: 2026-09-09. Status: **In validation**, not Verified.
- Scope delivered: concatenated scene narration is validated against the approved script after generation and before it can become the active scene plan. A documented normalization policy limits comparison-time changes to Unicode NFC, CR/CRLF to LF, zero-width removal, whitespace-run collapse and boundary trimming, with each rule justified in the module; case, punctuation, quotes, dashes, numerals and wording are never normalized. Missing, duplicated, reordered, invented and empty narration, plus an uncovered script tail, are rejected with a single actionable discrepancy naming the scene number, script character offset, the approved excerpt and the received excerpt. A difference that is purely punctuation is flagged `punctuationOnly` and reported rather than folded away. One bounded repair attempt re-prompts the provider with the discrepancy quoted back. Paid output that fails validation records provider request id, tokens and actual cost and reconciles its reservation; no scenes are written, so the previously usable plan is preserved. The scenes page compares approved-script narration to the current scene plan and marks the first divergence.
- Acceptance criteria met (plan V2-03): missing/duplicated/reordered/invented narration fails before becoming the active plan — met, unit-tested and enforced in the worker. Multilingual, punctuation, repeated-phrase and boundary-whitespace cases — met (Japanese, Arabic, decomposed Spanish, German wording change, smart quotes, changed question mark, repeated phrases, leading/trailing whitespace). Failed analysis preserves the previous usable plan and reports an actionable discrepancy — met, evidenced by a live PostgreSQL test asserting the prior three scenes and their narration survive a rejected run. Provider usage recorded when paid output fails validation, with bounded repair under existing budget/reservation/idempotency rules — met for recording and bounding; see the budget caveat below. Rendered scene narration comparable to the approved script during review — met via the coverage panel.
- Remaining criteria / next action: authenticated creator walkthrough of the coverage panel and of a real rejected run. No live provider generation was executed, so the repair prompt has never been exercised against a real model. Budget caveat: the preflight budget check in `startSceneAnalysis` is unchanged and still sizes a single call, so a run that uses its one repair can reconcile above its reserved amount, bounded at roughly twice the estimate. Reservations already reconcile to actual cost and nothing is spent without a reservation, but the estimate is not yet repair-aware; revisit if repair rates prove non-trivial in production.
- Architectural decisions and rationale: (1) Forward cursor matching rather than per-passage search, so a script that legitimately repeats a phrase passes while a plan covering one occurrence twice and the other not at all fails — a search-based check accepts exactly that corruption. (2) NFC and not NFKC, because compatibility folding rewrites `½` to `1/2` and `ﬁ` to `fi`, which changes what is written. (3) The walk stops at the first divergence; after coverage breaks there is no reliable resynchronization and downstream differences would be noise rather than an actionable report. (4) `failSceneAnalysisWithUsage` is separate from `failSceneAnalysis` because the existing path releases the reservation at zero, which is correct only when nothing was generated. (5) The review comparison is recomputed from current scene versions instead of stored, because scenes are editable after analysis and a stored verdict would describe a plan that no longer exists; this also removed any need for a migration. (6) `MAX_SCENE_ANALYSIS_REPAIR_ATTEMPTS` is a policy constant rather than an environment variable, so a deployment cannot silently raise billable retries. (7) The failure category lives in `lib/scenes/scene-analysis-failure.ts` so the review component can name it without importing Trigger.dev and server-only providers into the client bundle. All logic is text-structural and independent of channel, genre and language.

### V2-04 — Channel production profiles

- Owner: Claude. Started / last updated: 2026-09-09. Status: **In validation**, not Verified.
- Scope delivered: workspace-owned production channels that exist independently of OAuth. A channel carries name, platform, audience, tone, language, release cadence, IANA time zone and optional aspect-ratio and budget defaults. Projects gained an optional channel assignment, project creation accepts and validates one, and workspace settings gained a **Production channels** section listing each channel with its live publish availability and project count. Archived, never deleted.
- Central architectural decision — **no stored connection id**: a profile records only the platform's own `external_account_id`, and the live grant is resolved by joining on (workspace, platform, external account id) at read time. Pointing a profile at a `platform_connections` row would tie production identity to an OAuth grant that revocation deletes and reconnection recreates under a new id. With the identity join, a revoke leaves the channel and its entire project history untouched and merely reports `disconnected`, and a reconnect re-links automatically with no repair step. This is proven end to end by a live PostgreSQL test that connects, deletes the connection row outright, and reconnects.
- Second decision — **the composite foreign key had to be reworked**. The first generated migration used `ON DELETE SET NULL` on composite keys `(connection_id, workspace_id)` and `(channel_profile_id, workspace_id)`. PostgreSQL nulls _every_ column in a composite SET NULL, and `workspace_id` is NOT NULL, so deleting a connection or a profile would have failed outright at runtime. That migration was discarded before it was applied. The connection key was removed entirely by the identity-join design above, and the project key is now `ON DELETE CASCADE`, which is only safe because channel profiles are archived and never hard-deleted — there is deliberately no delete command, and the schema comment says so. Workspace deletion still cleans up through the existing workspace cascade, verified by fixture teardown leaving zero rows.
- Acceptance criteria: _multiple channels keep distinct profiles and project lists_ — met, live test asserts two channels plus an unassigned backlog resolve to disjoint project lists. _New projects inherit the intended channel; unassigned legacy projects remain usable_ — met, `channel_profile_id` is nullable, creation validates the channel against the workspace, and an unassigned project is exercised in the same test. _Profile assignment and defaults cannot reference another workspace's resources_ — met at two levels: the command refuses, and a raw update bypassing the command is rejected by the database itself, both asserted. _Reconnecting or revoking OAuth preserves production identity and history while blocking unavailable publication actions_ — met for identity, history and the availability state machine; `canChannelPublish` is only true for `ready`. _Upload targets come from explicit project/release selection, never an unrelated first active connection_ — **met**. The defect was real and it was in `selectInitialPublishingTarget`, which fell back to `connections.find(status === "active")` — whichever active account sorted first. It now follows an explicit order: an in-flight publication wins, then the project's assigned channel, and only then a sole active account. With two or more accounts connected and no channel assigned it selects nothing and makes the user choose rather than guessing. `loadPublishingView` resolves the channel's live connection and passes it through, and six tests cover the order, including a channel whose account is revoked, a channel id absent from the list, and an in-flight publication overriding the channel. An existing test that asserted the old first-active fallback was rewritten, with the reason recorded in the test itself. `findActivePlatformConnection` still exists and is used only by Marketing Studio auto-scheduling, out of scope by standing instruction.
