# Publishing connections

Accounts & connections at `/app/social/accounts` is the shared account-management page. Workspace owners can connect or disconnect accounts; editors can review their status and posting requirements. Every disconnect action resolves the authenticated workspace and owner capability on the server, validates the connection identifier, and scopes the lookup and update by both workspace and connection.

## Disconnect behavior

Use `DisconnectChannelDialog` for account disconnection in both the shared page and project publishing. Opening the dialog, cancelling it, or dismissing it must not call a server action. The dialog names the account and platform, explains that publication history is retained, and warns that scheduled posts may fail until reconnection. Focus starts on Cancel. Confirmation disables repeat submissions and dismissal until the request settles. Failure stays in the dialog with a retry option; success closes it, refreshes account data, and shows one Sonner success toast naming the platform and account. Cancellation and failed requests must not show a success toast. Transport failures display safe text without exposing internal errors.

The server service uses `createConnectionOAuthProvider` for connection lifecycle operations. It resolves the stored account identity so LinkedIn Pages use their dedicated app and profiles retain the personal app. Do not use `createVideoPublishProvider` here: LinkedIn and X support social posts without implementing rendered-video publishing. That mismatch previously threw `UnsupportedPlatformError` before disconnection reached the database, regardless of LinkedIn developer-app verification.

Where supported, remote authorization revocation is attempted. Provider construction, decryption, and revocation failure must not prevent clearing this workspace's credentials. A safe warning identifies the platform without logging tokens, encrypted credentials, app secrets, or raw provider errors. The database command clears both saved tokens and their expiry, marks the connection revoked, and retains the row for publication history. A database failure must still report failure. Successful shared-page mutations record the existing audit event and refresh the shared page.

LinkedIn's current OAuth adapter does not implement remote revocation. Disconnecting it removes this workspace's saved credentials; it does not claim to revoke the member's LinkedIn-side app consent. Adding remote revocation would need a separately verified provider implementation. No new scopes or app credentials are required for this local-disconnection fix.

## Facebook Page discovery

Facebook's consent selector and Graph's `/me/accounts` list can disagree. Selecting a Page in consent does not by itself create a VCStudio connection or establish that Meta will issue a usable Page token. The picker previously relied only on that list and provided no recovery when a selected Page was absent.

The picker now loads the managed-Page list without caching, deduplicates results and follows at most ten pages of 100 results. A final cursor without `paging.next` does not cause another request, and pagination always reconstructs the fixed Graph host rather than following a token-bearing URL. When the existing `FACEBOOK_APP_ID` and `FACEBOOK_APP_SECRET` are configured, server-only token inspection checks validity and the same app identity, reads only `pages_show_list` consent targets, and verifies at most twenty omitted targets with four requests in flight. Each target must return its exact ID, name and a nonempty Page access token. A failed supplemental lookup keeps already-verified Pages available and logs only fixed safe text. Requests have ten-second timeouts; this work runs only during connection, without polling or background tasks.

If a Page is still missing, use **Missing a Page? → Facebook Page ID → Find Page** on `/app/settings/workspace/facebook/select`. Enter the numeric ID shown in Facebook's selector or the Page's About section. The lookup uses the existing temporary user authorization; no password, app secret or token is entered by the user. It displays the verified Page name before offering **Connect Page**. Lookup alone never saves an account. If Meta refuses a Page token, the UI explains how to check the ID, Facebook's **Edit settings** selection and the person's permission to create Page content, then offers reconnection. Failed lookups retain the entered ID.

Discovery, lookup and connection resolve current owner capability and check the encrypted session's user, workspace, expiry and publishing flag before contacting Meta. Connection rechecks the exact submitted Page ID through Meta, then uses the existing encrypted, workspace-scoped upsert and audit event. It ignores submitted names, tokens and workspace values, and consumes the session only after saving. Only Page IDs/names cross a client boundary. Existing connected accounts remain independent. No additional OAuth scope is requested; the application cannot bypass a missing Meta grant, Page role or app permission. Business-portfolio-specific access restrictions still require correction in Meta if direct lookup is denied.

The direct lookup follows [Meta's official Page-token example](https://www.postman.com/meta/facebook/request/tass6hw/get-specific-page-access-token). Regression verification uses mocked provider/authentication calls and a real-CSS browser fixture; no real account is connected or posted to as a test. No schema migration, new variable or worker deployment is needed.

Verification passed 404 publishing regression tests, six browser journeys, formatting, lint, TypeScript, environment placement and the production build. ## TikTok sandbox connections

Connect/Add TikTok is a branded shadcn link that opens TikTok authorization directly. A server route reads `TIKTOK_API_CLIENT_KEY` and `TIKTOK_API_CLIENT_SECRET`; users do not enter developer credentials, account passwords or access tokens in VCStudio. The action shows connection progress, prevents repeated activation during navigation and resets when returning from TikTok.

Before connecting:

1. In [TikTok for Developers](https://developers.tiktok.com/apps/), open the app's Sandbox configuration. Enable Login Kit and Content Posting API with `user.info.basic` and `video.upload`.
2. Register the exact Login Kit callback derived from `APP_BASE_URL`, ending in `/api/tiktok/callback`. Production uses `https://vcstudio.veilcode.studio/api/tiktok/callback`. TikTok requires HTTPS; use an appropriate HTTPS development origin if testing locally, with matching app configuration and authenticated session.
3. Add every TikTok account you own and want to connect under Sandbox settings → Target users. TikTok currently permits ten target users per sandbox. Adding a target user must be completed in TikTok's developer portal.
4. Configure the sandbox app values once as `TIKTOK_API_CLIENT_KEY` and `TIKTOK_API_CLIENT_SECRET` in the local, Vercel web and Trigger.dev worker environments. Web uses them for authorization/code exchange; workers need the matching values to refresh tokens and upload. Keep these variables server-only. When moving to an approved app, use its matching credentials and reauthorize affected accounts; changing app credentials does not migrate OAuth grants.
5. In VCStudio, click Connect/Add TikTok and authorize the intended account on TikTok. VCStudio sends `disable_auto_auth=1` so TikTok displays authorization even when the browser has a valid TikTok session. This does not force an account chooser or log out the current account: check the displayed identity, then switch accounts or log out of TikTok and log in to the intended account before granting consent. A separate browser profile is an alternative; sign into VCStudio and complete the whole flow within that profile. Repeat for each account; existing connections stay intact. Reauthorizing the same TikTok account updates its existing connection. Do not overwrite deployment-wide credentials to switch user accounts.

The server rechecks current workspace ownership and `ENABLE_VIDEO_PUBLISHING` before starting and completing a connection. The configured-app route creates signed, expiring OAuth state bound to the authenticated user and workspace with platform `tiktok`; the callback verifies that binding before exchanging a code. Only the public client key, callback, requested scopes and opaque signed state are sent in the authorization URL. App secrets remain server-side. Missing app configuration returns safe accounts-page feedback.

The earlier custom sandbox flow remains supported internally for existing integrations, but its credential dialog is no longer the normal connect action. That flow validates supplied credentials with shared Zod contracts and uses the separate `tiktok:sandbox` state purpose plus an encrypted, HttpOnly, SameSite=Lax cookie scoped to `/api/tiktok`, expiring within ten minutes. Its callback checks signature, purpose, expiry, current user/workspace and the cookie's exact state. A lost or changed custom-flow cookie cannot fall back to configured credentials. Starting another custom flow supersedes an unfinished one in that browser.

Persisted sandbox credentials use the existing `PLATFORM_TOKEN_ENCRYPTION_KEY`, bound to workspace and external account inside the encrypted value. Safe read projections return `isSandbox` without returning the ciphertext. Sandbox connections appear as **TikTok · Sandbox** on Accounts & connections. Refresh, video/Social upload and remote revocation select the saved app on the server. A malformed or cross-account credential fails closed. Disconnect removes both OAuth tokens and the saved app credentials while retaining publication history. Reauthorizing the same external account updates its row; other accounts and workspaces are untouched.

Both flows use TikTok's existing OAuth/API endpoints. Existing account-specific sandbox credentials continue taking precedence for their saved connection during refresh, upload and revocation; configured-app connections use the shared server variables. Both runtimes still need the same existing encryption key. No new environment-variable name or schema change is required for one-click connections.

**Restrictions remain:** sandbox does not grant public direct posting. VCStudio requests only basic identity and inbox upload permissions; the creator must finish the post in TikTok. This does not claim approval for the production TikTok application. See [TikTok sandbox requirements](https://developers.tiktok.com/docs/en/add-a-sandbox) and [Login Kit web authorization](https://developers.tiktok.com/docs/en/login-kit-web).

### Connection flow

1. An owner chooses **Connect LinkedIn Page** in Accounts & connections. The authorize route signs state with a Page-specific purpose, binds it to the user/workspace, and sets a short-lived HTTP-only state cookie. The callback checks this browser cookie, the signature/expiry/purpose, current membership, and the Social posting feature flag before exchanging a code.
2. Tokens remain in an encrypted, purpose-bound, user/workspace-bound selection cookie for at most ten minutes, capped by access-token expiry. They are never placed in a query string, form field, client prop, or provider-error message. Oversized cookies fail safely.
3. `/app/social/accounts/linkedin-pages` reads at most ten ACL records at a time. It requests and considers only approved Page administrators, matching the administered-organization lookup requirement and fetches names only for eligible identities. Pagination is explicit, bounded, and does not prefetch provider data. The shadcn selector supports keyboard input, empty results, pending guards, cancellation, duplicate-click protection, and retries that retain the selected Page.
4. On confirmation the server resolves the owner/workspace again, verifies the selection cookie before any provider request, reloads the relevant member ACL page, and checks `ORGANIC_SHARE_CREATE` for that exact member/Page through Organization Authorizations. It ignores browser-supplied names, roles, workspace IDs, and tokens.
5. The existing workspace-scoped encrypted-credential command stores the trusted Page identity, records the existing connection audit event, consumes the scoped selection cookie, and returns to Accounts & connections. Cancellation clears the cookie without storing credentials. Add another Page through another connection flow; all Page requests use the same scope set.

Page administrators are supported by this initial flow; content-only roles are not offered because the metadata endpoint requires administrator access. The later organic-posting check is still mandatory and can reject inactive or otherwise unauthorized Pages.

### Stored identity and publishing

Page connections store a canonical `urn:li:organization:{id}` in the existing external-account identifier. Legacy personal-profile IDs remain unchanged, including numeric member IDs. This intrinsic provider identity distinguishes the accounts and selects the correct OAuth app during refresh/disconnection; a browser never chooses the app credentials. No schema change or migration is required. Accounts, composer destinations, and publication history distinguish LinkedIn Pages from profiles.

The social-post provider uses the exact organization URN as post author and media owner; profiles retain their person URN. Text and image posts reuse the existing queue, publishing permissions, and publication history. Video uploads now follow LinkedIn multipart initialization, bounded byte-range transfer, ordered ETag finalization, and bounded processing checks before creating the post. A part buffers at most 4 MiB; an ignored or inconsistent storage range fails before upload/finalization. Upload destinations are restricted to LinkedIn/CDN HTTPS hosts. Processing waits use the worker's existing durable wait callback. Ambiguous post-creation responses, including HTTP 5xx or a missing post identifier, require human inspection and are never automatically retried.

Programmatic refresh tokens depend on LinkedIn approval. When no refresh token is issued, expiry requires the owner to reconnect; the application does not manufacture long-lived credentials. LinkedIn Page disconnection clears this workspace's stored credentials without claiming remote consent revocation or revoking other connected destinations. No rendered-project LinkedIn publishing or additional background task was added.

Provider contracts were checked against [API permissions](https://learn.microsoft.com/en-us/linkedin/marketing/increasing-access?view=li-lms-2026-10), [Organization ACLs](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/organizations/organization-access-control-by-role?view=li-lms-2026-03), [Organization Authorizations](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/organizations/organization-authorizations/organization-authorizations?view=li-lms-2026-02), and the [Videos API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/videos-api?view=li-lms-2026-01).
